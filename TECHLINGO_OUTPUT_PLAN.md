# TechLingo Generator Output Contract — Implementation Plan

Goal: the generator emits a **TechLingo-native `course.json`** that maps 1:1 onto
the TechLingo app hierarchy and DB, so the importer is a trivial upsert + insert.

```
TLCourse    -> courses
TLModule    -> lessons        (our internal "Module")
TLUnit      -> units          (our internal "Lesson"; slo -> units.description)
TLQuestion  -> questions      (FK unit_id)
TLFlashcard -> unit_pages     (page_type="exercise")
```

`category_id` / `path_id` live above Course and are **not** generated — the
importer receives them as CLI params.

## Architecture: transform layer (not LLM-native emission)

The A1–A5 pipeline keeps producing our **rich internal models** (`models.py`).
A **deterministic transform** (`emit.py`) converts them to the TechLingo contract
(`techlingo_models.py`) right before writing `course.json`. Rationale: all the
error-prone derived fields (index-based `correct_answer`, type renames,
`import_key` slugs) are computed in code, not generated by the LLM, so they can't
drift. The internal model already carries exactly the rich data the `options`
jsonb needs.

## Output files per run

- `course.json` — **TechLingo-native** (importer consumes this).
- `course.internal.json` — rich internal model (viewers/debug).
- `validation_report.json`, `course.md`, `artifacts/*.json` — unchanged.

## Phase-0 decisions (confirmed)

1. **Idempotency / `import_key`** — positional keys:
   - question: `<unit-key>-q<idx>` (1-based, matches `question_number`)
   - flashcard: `<unit-key>-f<idx>` (0-based, matches `page_order`)
   - course/module/unit keys are slugs of title (unit/module de-duped with `-2`, `-3`).
   Importer upserts by unit + slot; re-runs update the slot, never duplicate.
2. **Course key** — `--course-key ai-900`; fallback = slug of title.
3. **Viewers** — `course.json` becomes native; internal format preserved as
   `course.internal.json` until viewers are migrated.
4. **`multiple_choice` `correct_answer`** — index-based: single `"0"`, multi
   compact `"[0,1]"`.
5. **`fill_blank` `correct_answer`** — one accepted answer → plain string; multiple
   → compact JSON array string (keeps valid alternatives).
6. **`fill_gaps`** — exactly one gap per question (mobile has one input).
7. **`arrange_sentence` `correct_answer`** — joined `correct_order` string
   (mobile builds words via `.split(" ")`).
8. **`options` jsonb metadata** — `blooms_level`, `original_question_type`, rich
   option metadata (`rationale`/`error_type`/`better_fit`/`feedback`), `parts`
   (fill_blank), `word_bank`/`correct_order` (arrange).
9. **Validation** — output gate fails the run if the emitted course is not native.

## Type mapping

| Internal | TechLingo | `correct_answer` |
|---|---|---|
| `single_choice` | `multiple_choice` | index of correct, e.g. `"0"` |
| `multi_choice` | `multiple_choice` | compact index array, e.g. `"[0,1]"` |
| `true_false` | `true_false` | `"true"` / `"false"` (question_text = statement) |
| `fill_gaps` | `fill_blank` | accepted answer, or JSON array string |
| `rearrange` | `arrange_sentence` | joined `correct_order` |
